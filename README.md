# remnanode-bootstrap

Интерактивный скрипт разворачивания Remnawave-ноды на чистой VPS (Debian 12/13, Ubuntu 22.04/24.04).

Ставит всё сам, без сторонних установщиков: пишет `docker-compose.yml`, `.env` и конфигурацию, выпускает сертификат, регистрирует WARP, поднимает контейнеры и службы.

Поверх этого — проверки, диагностика и обход известных граблей: конфликта SSH-дропинов от хостера, падения регистрации аккаунта acme.sh и несовместимости версий ноды и панели.

## Быстрый старт

Запускайте под `tmux` или `screen`: на шагах 3 и 5 придётся уйти в браузер, а apt и выпуск сертификата идут минутами. Если SSH-сессия оборвётся (телефон уснул, сеть мигнула), установка без мультиплексора умрёт посреди шага. Скрипт проверяет это сам и предупреждает.

```bash
apt-get update && apt-get install -y tmux curl ca-certificates
tmux new -s rn          # после обрыва: tmux attach -t rn
```

### Скачать, прочитать, запустить (рекомендуется)

```bash
curl -fsSL -o bootstrap.sh https://raw.githubusercontent.com/alekvol/remnanode-bootstrap/main/bootstrap.sh
less bootstrap.sh       # скрипт меняет sshd_config, ufw, cron и systemd от root — стоит прочитать
bash bootstrap.sh       # или sudo bash bootstrap.sh
```

Этот способ работает и через `sudo`, и из любой оболочки (dash, fish), а если скачать не удалось, `curl` честно вернёт ошибку.

Чтобы запустить ровно ту версию, которую вы прочитали, а не текущий `main`, подставьте в ссылку тег или хеш коммита вместо `main`: `https://raw.githubusercontent.com/alekvol/remnanode-bootstrap/<тег-или-коммит>/bootstrap.sh`.

### Одной командой

Только из root-шелла (`sudo -i`, затем команда):

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/alekvol/remnanode-bootstrap/main/bootstrap.sh)
```

У однострочника два ограничения:

- **Не работает через sudo.** `sudo bash <(curl ...)` падает с `bash: /dev/fd/63: No such file or directory`: sudo закрывает дескрипторы, через которые подставляется скрипт. Это синтаксис bash, в dash или fish он не сработает вовсе.
- **Возвращает 0, даже если скачать скрипт не удалось.** `curl` печатает ошибку, а `bash` исполняет пустой ввод и выходит успешно. Для cloud-init и другой автоматизации скачивайте в файл. Хотя скрипт интерактивный и без терминала откажется работать.

Пайп `curl ... | bash` тоже не ломает ввод: весь диалог и stdin дочерних процессов скрипт берёт из `/dev/tty`. Но у пайпа те же два ограничения.

Требования: root, Debian или Ubuntu, bash 4+, интерактивный терминал. Всё остальное скрипт доставит сам.

## Что делает

| Шаг | Действие |
|---|---|
| 1 | Базовые пакеты |
| 2 | Вход по SSH-ключу, отключение паролей |
| 3 | Tailscale (с `--ssh` как запасной канал) |
| 4 | Проверка A-записи домена (можно пропустить) |
| 5 | Своя установка ноды: docker compose, .env, том для unix-сокета |
| 6 | Свой nginx: контейнер, unix-сокет, сертификат через HTTP-01, стоковая заглушка |
| 7 | Свой WARP: wgcf, `wg-quick@warp` с `Table = off`, watchdog |
| 8 | ufw: наружу только 22, 80 и 443, порт ноды — только на `tailscale0` |
| 9 | BBR + fq |
| 10 | Инбаунд VLESS XHTTP поверх REALITY: генерация JSON для панели |

Каждый шаг можно пропустить. Пройденные шаги записываются в `/var/lib/remnanode-bootstrap/state`, поэтому скрипт безопасно перезапускать — он предложит пропустить сделанное.

Если шаг не удался, остальные всё равно выполняются: неудача WARP не оставит сервер без файрвола. Итог отмечает незавершённые шаги, а скрипт выходит с кодом 1.

## Решаемые проблемы

### SSH: дропины хостера перекрывают harden-конфиг

Провайдеры кладут в `/etc/ssh/sshd_config.d/` файлы вроде `00-hostup-auth.conf` и `50-cloud-init.conf` с `PasswordAuthentication yes`. Файлы читаются по алфавиту, и sshd применяет **первое встреченное** значение — поэтому дропин `99-hardening.conf` не работает.

Скрипт пишет директивы в основной `sshd_config` **перед строкой `Include`**, что перекрывает и дропины, и раскомментированные провайдером строки ниже по файлу. Дополнительно в `/etc/cloud/cloud.cfg` добавляется `ssh_pwauth: false`, чтобы cloud-init не восстановил свой файл после перезагрузки.

Блок обрамлён маркерами `# >>> remnanode-bootstrap` / `# <<<`, так что повторный запуск не дублирует его, а исходные строки провайдера остаются на месте — они просто перекрыты.

Пароль отключается только после трёх подряд подтверждений: скрипт считает ключи в `authorized_keys` (через `ssh-keygen -l`, так что строки с опциями и FIDO-ключи `sk-*` тоже учитываются), при нуле ключей харденинг пропускается молча. Дальше он останавливается и просит проверить вход по ключу из отдельного окна, потом требует ввести `YES` заглавными. После записи конфига результат сверяется по `sshd -T -C` для входа root снаружи: без `-C` sshd показывает только глобальные значения, а `Match`-блок из дропина провайдера (`Match User root` → `PasswordAuthentication yes`) молча вернул бы пароль. Найденные `Match`-блоки скрипт показывает. Если `sshd -t` забраковал конфиг — автоматически восстанавливается бэкап.

### SSH: socket-активация в Debian 13 и Ubuntu 24

Там порт 22 слушает `ssh.socket`, а не постоянно запущенный демон. Привычный `systemctl reload ssh` падает с `fatal: Cannot bind any address`. Скрипт определяет режим и делает `restart ssh.socket` либо `reload ssh` соответственно.

### acme.sh: не регистрируется аккаунт

Готовые установщики при первой установке acme.sh генерируют случайный e-mail вида `user12345@$(hostname -f)`. Если у хоста короткое имя без домена (`stellar-gecko`), адрес получается невалидным и Let's Encrypt отклоняет регистрацию аккаунта.

Скрипт ставит acme.sh заранее с настоящим e-mail, переключает CA на Let's Encrypt и явно регистрирует аккаунт.

### Сертификат: почему HTTP-01, а не TLS-ALPN

Распространённый вариант — выпускать сертификат через TLS-ALPN на 443. Но в этой схеме 443 принадлежит Xray под REALITY, и при **продлении** acme.sh не сможет туда забиндиться: установщики обходят это редиректом через iptables на другой порт.

Скрипт идёт прямее: HTTP-01 через webroot, который обслуживает тот же nginx на порту 80. Продление не требует ни останова контейнера, ни правил iptables и отрабатывает само из крона acme.sh — `--reloadcmd` перечитывает конфиг nginx (`nginx -s reload`) с новым сертификатом.

Сертификат всегда ведёт acme.sh — просто скопированный файл никто бы не продлевал:

- acme.sh уже ведёт сертификат домена через наш webroot — новый не выпускается (у Let's Encrypt лимит 5 одинаковых сертификатов в неделю), только продлевается, если пора;
- acme.sh ведёт его другим способом (например, TLS-ALPN от прежнего установщика) — сертификат один раз перевыпускается через webroot, иначе продление на занятый Xray порт 443 провалится. Если перевыпуск упёрся в лимит, ставится прежний действующий сертификат, а продлит его уже webroot;
- старый RSA-сертификат того же домена снимается с автопродления, чтобы его крон не дёргал остановленную прежнюю установку.

После установки сертификат сверяется с доменом (по SAN) и сроком действия — в том числе при повторном запуске, если домен сменили на шаге 4.

## После установки

Скрипт не трогает конфиг Xray — он живёт в панели Remnawave, а не на ноде. Добавьте outbound вручную:

```json
{
  "tag": "warp",
  "protocol": "freedom",
  "settings": { "domainStrategy": "UseIPv4" },
  "streamSettings": {
    "sockopt": { "interface": "warp", "tcpFastOpen": true }
  }
}
```

Порядок в массиве `outbounds` важен: первый элемент — маршрут по умолчанию, поэтому `DIRECT` держите первым. Теги в правилах `routing` сверяются посимвольно — `DIRECT` и `direct` разные вещи.

### Почему `settings.domainStrategy: UseIPv4`, а не `AsIs` + sockopt

Документация XTLS предлагает связку `settings: AsIs` + `sockopt.domainStrategy`, чтобы работал happyEyeballs. На серверной стороне она не срабатывает: для инбаундов VLESS активна политика безопасности Freedom по умолчанию, из-за которой применяются `finalRules`, а при них домен резолвится через системный DNS **до** матчинга правил — и `sockopt.domainStrategy` теряет силу.

Резолв в самом Freedom использует секцию `dns` конфига, что и нужно. `sockopt.interface` при этом работает независимо от резолва.

## Установка ноды

Шаг 5 не вызывает внешний установщик, а пишет файлы сам:

- `/opt/remnanode/.env` — `NODE_PORT` и `SECRET_KEY`, права 600. Существующие значения переиспользуются: при повторном запуске ключ из панели заново вводить не нужно. Если вставить из панели всю строку `SECRET_KEY="eyJ..."`, лишнее отрежется, а ключ, не похожий на base64, скрипт не примет.
- `/opt/remnanode/docker-compose.yml` — образ `ghcr.io/remnawave/node`, `network_mode: host`, `cap_add: NET_ADMIN`, лимит дескрипторов.
- `/usr/local/bin/rn` — обёртка над `docker compose` вместо CLI, который ставил внешний скрипт: `rn ps`, `rn logs -f`, `rn restart`, `rn down`.

Docker ставится из официального репозитория. На производных дистрибутивах (Mint, Pop!_OS) берётся база из `ID_LIKE` с её кодовым именем. Если установка не удалась, `docker.list` убирается, чтобы не ломать следующие `apt-get update`. Если Docker уже стоит из пакета дистрибутива (`docker.io`) без compose, плагин доставляется отдельно.

Плюс том, которого нет в установке по умолчанию: `/dev/shm:/dev/shm`. Через него нода видит unix-сокет, который создаёт соседний контейнер с nginx, — туда REALITY отдаёт чужой трафик. У внешнего установщика эта строка лежала закомментированной.

### Версия образа и совместимость с панелью

Нода 3.3.0 и новее рвёт TLS-хендшейк, если панель старее 3.3.0: панель не шлёт производный SNI, нода закрывает соединение, не отдав ни байта, и в её логах появляется `unknown sni`. Снаружи это выглядит как «нода офлайн» без внятной причины.

Поэтому шаг спрашивает версию панели и при старой подставляет тег `3.2.2`. После запуска логи проверяются на `unknown sni` — если он есть, скрипт скажет прямо.

## Selfsteal

Шаг 6 поднимает nginx контейнером в `/opt/selfsteal`:

| Файл | Что внутри |
|---|---|
| `nginx.conf` | базовые настройки, логи в `crit`, `server_tokens off` |
| `conf.d/selfsteal.conf` | слушатель на 80 и слушатель на unix-сокете |
| `html/index.html` | страница-заглушка — стоковая «Welcome to nginx!» |
| `ssl/` | сертификат, сюда же кладёт продление acme.sh |
| `acme/` | webroot для ACME-челленджа |

Слушателя два, и у каждого своя роль:

```nginx
listen 80 default_server;                        # ACME-челлендж и редирект на https
listen unix:/dev/shm/nginx.sock ssl proxy_protocol;   # сюда REALITY отдаёт чужой трафик
```

На сокете `ssl` обязателен: при `xver: 1` REALITY передаёт TLS-рукопожатие как есть, и терминирует его nginx. `proxy_protocol` — оттуда же: без него Xray шлёт заголовок, который nginx не ждёт, и соединения рвутся.

Сокет лежит в `/dev/shm`, который примонтирован в оба контейнера: создаёт его nginx, читает нода. Файл живёт там до перезагрузки хоста. Если nginx убит через SIGKILL (`docker kill`, OOM, истёк таймаут `docker stop`), он не убирает сокет за собой, и следующий старт падал бы с `Address already in use`. Поэтому `entrypoint` контейнера удаляет сокет перед запуском nginx.

Заглушка — стоковая страница «Welcome to nginx!», взятая из того же образа. Её отдают миллионы свежих серверов, так что ноду по ней не выделить. Своя страница, одинаковая на всех установках скриптом, наоборот, позволяла бы найти все такие ноды по хешу. Свою страницу можно положить в `html/`: при повторном запуске она не перезаписывается. Заменяется только заглушка «Service is being set up» из прошлых версий.

Прежняя установка от внешнего скрипта (`/opt/nginx-selfsteal`, `/opt/caddy`) занимает и порт 80, и тот же сокет. Скрипт её находит и предлагает остановить; файлы при этом не трогаются, так что откат — это `docker compose up -d` в старом каталоге.

## XHTTP поверх REALITY

Шаг 10 добавляет второй инбаунд рядом с уже работающим REALITY — конфиг Xray живёт в панели, поэтому скрипт только генерирует JSON, а вставляете его вы.

Схема взята из официального примера [VLESS-XHTTP-REALITY / steal_oneself](https://github.com/chika0801/Xray-examples/blob/main/VLESS-XHTTP-REALITY/steal_oneself/config_server.json):

```
клиент REALITY + XHTTP ──► 443, инбаунд REALITY
                             │
                             ├─ не прошёл проверку REALITY ──► realitySettings.target
                             │                                 = /dev/shm/nginx.sock (nginx, сайт-заглушка)
                             │
                             └─ прошёл, но внутри не VLESS ──► fallback ──► @xhttp (инбаунд XHTTP)
```

XHTTP слушает **абстрактный unix-сокет** `@xhttp`: TCP-порт не занимается, наружу ничего не выставляется, nginx в цепочке не участвует и его конфигурация не меняется.

Абстрактные сокеты принадлежат сетевому пространству имён, а нода работает в `network_mode: host`, поэтому `@xhttp` виден всему хосту, а не только контейнеру. Прав доступа у таких сокетов нет. Чужих он всё равно не пустит: VLESS проверяет UUID клиента.

### Почему fallback без `path`

Напрашивается разбор по пути — `{"path": "/xhttp", "dest": ...}`. Так делать не надо: разбор по `path` на xhttp работает некорректно, это [известный баг Xray-core #4832](https://github.com/XTLS/Xray-core/issues/4832).

Поэтому fallback один и без условий:

```json
"fallbacks": [ { "dest": "@xhttp" } ]
```

Путь проверяет сам XHTTP-инбаунд и отвергает чужие запросы. `realitySettings.target` и `xver: 1` при этом остаются прежними — трафик, не прошедший проверку REALITY, как и раньше уходит в nginx.

## WARP

Шаг 7 регистрирует аккаунт через [wgcf](https://github.com/ViRb3/wgcf), правит профиль под `wg-quick` и поднимает `wg-quick@warp`.

Ключевая строка в `/etc/wireguard/warp.conf`:

```ini
Table = off
```

Без неё `wg-quick` добавит маршрут по умолчанию через WARP, и **весь** трафик сервера уйдёт в Cloudflare — вместе с ответами SSH и связью с панелью. С ней интерфейс просто поднимается, а в туннель попадают только сокеты, привязанные к нему через `sockopt.interface` в конфиге Xray.

Строка ставится сразу после `[Interface]`, а прежние `Table` из профиля удаляются: `wg-quick` берёт последнее значение. Скрипт проверяет результат дважды. Без `Table = off` в профиле служба не запускается вовсе. После запуска ядро спрашивают, куда уйдёт обычный пакет (`ip route get 1.1.1.1`). Смотреть на `ip route show default` бесполезно: без `Table = off` wg-quick не трогает main-таблицу, а добавляет правило по fwmark и свою таблицу 51820.

Из профиля также убирается строка `DNS` — иначе `wg-quick` переписал бы системный резолвер целиком, — и добавляется `PersistentKeepalive = 25`. Если на хосте выключен IPv6 (`ipv6.disable=1` или sysctl `disable_ipv6`), из `Address` и `AllowedIPs` вырезаются только IPv6-токены: обе строки содержат и IPv4, и удалять их целиком нельзя.

Вариант B живёт, пока туннель работает, поэтому ставится watchdog: `/usr/local/bin/warp-watchdog` раз в пять минут запускается из `/etc/cron.d/warp-watchdog`. Он перезапускает службу, если интерфейс пропал или handshake с Cloudflare не обновлялся больше пяти минут (интерфейс на месте, а туннель мёртв). Службу, остановленную или выключенную вручную, watchdog не трогает.

Повторный запуск шага не перерегистрирует аккаунт без спроса. Существующий профиль (свой или от `wtm.sh`) приводится к варианту B так же, как новый, и служба перезапускается. Ставятся недостающие `wireguard-tools` и watchdog. После перерегистрации служба именно перезапускается: `enable --now` уже работающую не тронул бы, и интерфейс остался бы со старыми ключами.

## Файрвол

Шаг 8 ставит ufw и приводит правила к такому виду:

| Что | Кому открыто |
|---|---|
| 22/tcp (или порт из `sshd -T`) | всем |
| 80/tcp | всем — нужен на время выпуска сертификата |
| 443/tcp | всем — VLESS REALITY и selfsteal |
| порт API ноды | только на интерфейсе `tailscale0` |
| 41641/udp | всем, если разрешили (по умолчанию да) |
| всё остальное входящее | запрещено |

Порт ноды скрипт читает сам из `/opt/remnanode/.env` (ключ `NODE_PORT`, у старых установок `APP_PORT`), спрашивает только если не нашёл. Порт SSH берётся из `sshd -T`, а не из конфига: он мог быть переопределён дропином, а закрыться от самого себя нельзя.

Правило для SSH добавляется **до** `ufw enable`. Если его нет ни в `ufw show added`, ни в `ufw status`, скрипт откажется включать файрвол. После включения правило проверяется ещё раз, и если его не видно, ufw тут же выключается, пока текущая сессия жива.

Перед применением скрипт смотрит, кто сейчас подключён к порту ноды. Если это адрес не из тейлнета (скорее всего панель ходит к ноде по публичному IP), он предупреждает: после `ufw enable` панель потеряет связь, и нода уйдёт в офлайн. Адрес ноды в панели нужно сменить на тейлнет-адрес (`tailscale ip -4`).

### Tailscale обходит ufw

В режиме по умолчанию (`--netfilter-mode=on`) tailscaled ставит переход в свою цепочку `ts-input` первым правилом INPUT. Это та же таблица `filter`, которой через iptables-nft пользуется ufw. В `ts-input` лежат `-i tailscale0 -j ACCEPT` и `-p udp --dport 41641 -j ACCEPT`. ufw запрещает входящее политикой цепочки, а не явным DROP, поэтому эти ACCEPT срабатывают при любом порядке правил.

Итог: **весь** трафик из тейлнета и 41641/udp пропускаются раньше ufw. Ограничить устройства тейлнета одним портом ufw не может, это делается ACL в админке Tailscale. Скрипт это обнаруживает, сообщает и не задаёт вопросов «узко или широко» и «открывать ли 41641»: ответы ни на что бы не влияли. Узкое правило для порта ноды и правило для 41641 он всё равно добавляет, на случай `--netfilter-mode=off`.

Если tailscaled работает без своих правил (`--netfilter-mode=off` или `nodivert`), вопросы задаются как раньше. Доступ из тейлнета можно открыть узко (только порт ноды) или широко (весь интерфейс).

### Про 41641/udp

Tailscale слушает этот порт для прямых соединений между пирами. При неудачной пробивке NAT трафик пойдёт через DERP-релеи: лишняя задержка и чужой сервер в маршруте, что для пары панель↔нода заметно. Риска в открытом порте нет: там WireGuard, пакет от неаутентифицированного пира отбрасывается на уровне криптографии. В режиме по умолчанию tailscaled открывает порт сам (см. выше); без его правил порт по умолчанию разрешён, но вопрос задаётся.

### Что ufw не закрывает

Docker пишет правила напрямую в цепочку `DOCKER-USER`, минуя ufw, поэтому порты, опубликованные через `-p`, остаются доступными снаружи даже при `deny incoming`. Для ноды это не проблема, пока её контейнер работает в `network_mode: host` — тогда слушает сам хост и ufw действует. Скрипт после включения перечисляет контейнеры с опубликованными портами, если такие есть.

## Диагностика

```bash
ufw status verbose                # действующие правила
rn ps                             # состояние ноды
rn logs -f                        # логи контейнера
systemctl status wg-quick@warp    # состояние WARP
ip -br a show warp
wg show warp latest-handshakes    # время последнего handshake с Cloudflare
ip route get 1.1.1.1              # dev должен быть НЕ warp
curl --interface warp https://www.cloudflare.com/cdn-cgi/trace   # ждём warp=on
journalctl -t warp-watchdog       # перезапуски от watchdog
sshd -T | grep -iE 'password|permitroot'
journalctl -t sshd -n 30          # логи SSH при socket-активации
```

Лог установки: `/var/log/remnanode-bootstrap.log`
Бэкапы изменённых конфигов: `/root/remnanode-bootstrap-backups/`

## Откат

```bash
# вернуть sshd_config
cp /root/remnanode-bootstrap-backups/sshd_config.<дата> /etc/ssh/sshd_config
sshd -t || echo "конфиг с ошибкой — не перезапускайте sshd"
# применить: при socket-активации (Ubuntu 24.04) — перезапуск сокета,
# иначе (Debian 12 и др.) — reload службы
if systemctl is-active --quiet ssh.socket; then systemctl restart ssh.socket; else systemctl reload ssh; fi

# выключить файрвол
ufw disable

# сбросить состояние, чтобы пройти шаги заново
rm /var/lib/remnanode-bootstrap/state
```

Удаление ноды: `rn down` и `rm -rf /opt/remnanode`. WARP: `systemctl disable --now wg-quick@warp`, затем `rm /etc/wireguard/warp.conf /etc/cron.d/warp-watchdog`.

## Ограничения

- Проверялось на Debian 13 (trixie) и Ubuntu 24.04, x86_64
- На контейнерной виртуализации (LXC, OpenVZ) часть sysctl доступна только на чтение: шаг 9 сообщит, что `default_qdisc` не применился, и пойдёт дальше; WARP там часто не поднимется без модуля wireguard в ядре хоста
- Файрвол настраивается только через ufw; если на сервере уже правила nftables или iptables мимо ufw, шаг 8 их не учитывает. Трафик тейлнета tailscaled пропускает сам, мимо ufw — см. «Tailscale обходит ufw»
- Проверку «порт ноды закрыт снаружи» скрипт делает по списку правил ufw, а не реальным подключением извне — сканировать себя снаружи он не может, поэтому подсказывает команду для проверки с другой машины
- Вариант B WARP требует `network_mode: host` у контейнера ноды; скрипт пишет это в compose сам
- Не редактирует конфиг Xray: он управляется панелью

## Разработка

Скрипт — один файл на bash с `set -Eeuo pipefail`. Перед коммитом:

```bash
bash -n bootstrap.sh && shellcheck -S warning bootstrap.sh
```

Вещи, на которых тут уже обжигались, — стоит держать в голове при правках:

- **Имена глобальных констант.** `preflight` читает `/etc/os-release`, где определены `VERSION`, `NAME`, `ID` и другие расхожие имена. Читается он в субшелле, но новые `readonly` всё равно называйте с префиксом (`BOOTSTRAP_*`).
- **`grep -c` возвращает 1 при нуле совпадений** — значит `$(grep -c ... || echo 0)` под `pipefail` даёт строку `"0\n0"`, а не `0`, и следующая же арифметика ломается. Для подсчёта ключей есть `count_keys()`.
- **`die` внутри функции убивает весь скрипт.** Если вызывающий рассчитывает пережить неудачу (`step || { warn; return 0; }`), внутри нужен `err` + `return 1`.
- **Шаги вызываются через `run_step`, и внутри них `set -e` не действует.** Функция, вызванная в контексте `||`/`&&`, выполняется с выключенным errexit — так устроен bash. Поэтому каждую важную команду в шаге проверяйте явно (`|| { err ...; return 1; }`), а не надейтесь, что упавшая команда остановит шаг.
- **`cmd | grep -q` под `pipefail` может «не найти» найденное.** grep выходит на первом совпадении, `cmd` получает SIGPIPE, и код пайпа становится ненулевым. Длинный вывод сначала сохраняйте в переменную.
